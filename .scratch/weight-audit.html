Variable-Weight Products

Can NOBO sell fish, meat and cheese by measured weight — manually entered, and later from an electronic scale — without breaking anything that sells by the piece today? This report traces the actual code to answer that, section by section, before a single line is written.

You can already sell 1.350 kg of fish at 250 EGP/kg today, with zero migration. Create a variant whose sales unit is KG (fractional quantities already allowed) and price it at 250 in the price list — the server multiplies price × decimal quantity correctly and stores 1.3500 safely. What's genuinely missing: an explicit marker that a sale is a weighed sale, a same-dimension check between the sales unit and the stock unit, a modifier-pricing decision for weighed items, a unit price on the printed receipt, and — for the scale half of this — a way for a reading to travel from any local device into the cloud and back to the POS, which doesn't exist on any path today.

A. Product / Variant model

Verified

Product (src/Nobo.Domain/Catalog/Products/Product.cs) carries no unit, price or weight field — just identity, category, tax category, name/description/image, sort order and status.

The selling unit lives one level down, on ProductVariant (src/Nobo.Domain/Catalog/Products/Variants/ProductVariant.cs): a required SalesUnitOfMeasureId. It's fixed at creation — UpdateDetails(name, sku, sortOrder) cannot change it, and UpdateProductVariantCommand has no unit field either. CreateProductVariantHandler checks the unit exists and is active, but never looks at its dimension.

The selling unit and the inventory unit are genuinely separate things: inventory lives on InventoryItem.BaseUnitOfMeasureId, linked to the variant only through ProductVariantInventoryComponent.QuantityPerSalesUnit (see H).

There is no "sold by weight" concept anywhere in the domain — confirmed by a repo-wide search for SoldByWeight, SellingMode, PricingMode, IsWeighed, ByWeight, ConversionFactor (nothing outside migrations). Quantity validation already requires a decimal > 0, at most 4 decimal places, and a whole number only when the unit's AllowsFractionalQuantity is false (ValidateQuantity in both CreateDraftSalesOrderHandler and UpdateDraftSalesOrderHandler).

Answers

A. There is no dedicated place for this distinction today — it would be new. B. The model can represent a weighed product today purely by giving it a fractional unit (KG/G), but it can't say it's weighed — that's implicit, derived from the unit, not an explicit fact anywhere. C. The natural home is the variant (one variant = one selling mode + one unit, already the case), not the product (a product can have piece and weighed variants side by side) and not the price list (which just holds an amount). D. Any new column defaults to the existing per-piece behavior (e.g. a SellingMode enum defaulting to PerUnit = 1) — every existing variant and historical line is untouched.

UnitOfMeasure (src/Nobo.Domain/ReferenceData/UnitsOfMeasure/UnitOfMeasure.cs) has no CompanyId — units are global, not per-company. It has Code, Name, Symbol, MeasurementDimension, AllowsFractionalQuantity, IsActive — no conversion factor, no base-unit link.

Seeded by UnitOfMeasureReferenceDataSeeder.cs with fixed GUIDs. MeasurementDimension (Count / Mass / Volume / Length / Time) already separates mass from everything else — but nothing in the code reads it today for validation or conversion.

A product's selling unit can already differ from its inventory unit — sell in KG, stock in G is representable right now — but nothing enforces that the two even measure the same thing (a KG sale against an EA-tracked item is accepted silently).

C. Price lists & calculation

Verified

PriceListItem holds a flat Amount (numeric(18,4)) per (price list, variant) — implicitly "per one sales unit," never stated explicitly. The line subtotal is computed server-side, in plain decimal arithmetic, in both CreateDraftSalesOrderHandler (~line 518) and UpdateDraftSalesOrderHandler (~line 538):

unitPrice = variant.BaseUnitPrice + modifierUnitAdjustmentTotal;
lineSubtotalAmount = unitPrice * input.Quantity;

Nothing here assumes an integer piece count — 250 × 1.350 already comes out to 337.50 correctly today.

Snapshotting: SalesOrderLine copies BaseUnitPrice, ModifierUnitAdjustmentTotal, UnitPrice, LineSubtotalAmount at the moment of sale; SalesOrder.PriceListNameSnapshot records the list's name too. A later price-list edit never touches a past line.

Rounding: SalesOrderDiscountCalculator.RoundSnapshotAmount rounds to 8 decimal places, MidpointRounding.AwayFromZero, used for discount allocation and tax. SettlementMonetaryRoundingPolicy.Round rounds only the final PayableAmount to the currency's own decimal digits. No banker's rounding anywhere.

Inferred risk A weight like 1.3333 kg × 250 gives 333.325, kept at 8 decimals; only the order's payable gets rounded to currency digits. Line-level displays can therefore fail to add up to the payable to the last digit — already true today for any fractional-unit sale, but weighed sales will make it common and visible.

Answers

A price-per-kg is already representable with zero change (just price the variant). The amount is not tied to a unit explicitly — if a variant's unit could ever change post-creation, an existing price would silently change meaning (it can't change today, which is the only reason this is safe). The server always computes the final line amount; the client only ever sends quantity. Rounding currently has no fixed policy for permitted fractional weights — this should be decided, not assumed.

Answers (A–J)

  • A/B. Quantity is already decimal, at numeric(18,4) — 1.350 fits comfortably.
  • C. Unit prices are (18,4); monetary totals are (28,8).
  • D. No [Range] attribute, no DB check constraint anywhere restricts quantity to a whole number. The only integer rule is ValidateQuantity consulting the unit's AllowsFractionalQuantity — purely unit-driven, not hardcoded.
  • E. Yes — 1.350 is safely representable today (3 of the 4 available decimal places). A quantity with 5+ decimals is rejected, not silently rounded.
  • F. No — the line has no flag or snapshot that says "this was weighed." The only hint is the unit snapshot (code/name/symbol), not a dimension or mode marker.
  • G. Product/variant/SKU names, unit identity, quantity, all three price fields, line subtotal, tax category identity and rate, plus modifier names/amounts — all copied at SalesOrder.AddLine.
  • H. The server always computes the total. CreateDraftSalesOrderLineInput carries only (ProductVariantId, Quantity, ModifierOptionIds) — no price, no total, ever accepted from a client.
  • I. Discounts are allocated proportionally to pre-discount line subtotal (SalesOrderDiscountCalculator), rounded to 8 decimals, remainder to the last eligible line. Tax is grouped per category, inclusive/exclusive modes both handled.
  • J. Yes — the existing pipeline accommodates decimal/weighed quantities with minimal changes; the gaps are all about marking and displaying a weighed sale, not about the arithmetic.

Inferred risk Modifier adjustments are added to unit price before multiplying by quantity — a "+5 EGP sauce" on 1.350 kg of fish bills 6.75 EGP, not 5. Weighed variants likely need per-line (not per-weight-unit) modifiers, or no modifiers at all — a product decision, not a code fact.

E. POS cart & product-selection flow

Verified

Every add-to-cart path — a plain card tap, the per-variant quantity rows, a barcode scan — funnels through one function: addSellableVariant in src/Pages/POSPage/POSPage.jsx (~line 1627). Today it hardcodes the delta to exactly +1:

if (existing) { existing.quantity = Number(existing.quantity) + 1; }
else { requestLines.push({ productVariantId, quantity: 1, modifierOptionIds }); }

The commit path is a serialized queue (useDraftLineEditor.js, enqueue/changeQuantity) that batches rapid clicks for 280ms, then PUT /sales-orders/{id}/draft. It is delta-based only — there is no "set this line to exactly X" call anywhere in the frontend.

The catalog data already carries what's needed to detect a weighed product: every variant object the card handles already has salesUnitOfMeasure: { id, code, name, symbol, allowsFractionalQuantity } (features/pos/types/sellableCatalog.types.ts) — from the same GET /catalog/sellable response the card already consumes.

A reusable numeric-entry dialog already exists and is already used for editing a cart line's quantity: NumericKeypadModal.jsx → NumericKeypadCore.jsx, with props for allowDecimal, maxDecimalPlaces (currently used at 2, with allowDecimal={false} for the existing quantity-edit flow) and a unitLabel that's already wired up but unused for this purpose. The quantity model in the cart line type (DraftSalesOrderLine.quantity: number) and the request type (DraftSalesOrderLineInput.quantity: number) already accept a decimal — nothing stops a fractional value from being sent today except the UI never producing one.

Verified A now-unused variant/modifiers picker dialog (OrderDialogs.jsx, modal === "variant" / "modifiers") is still fully built and rendered, just never opened from the product grid anymore (confirmed: no call-site sets that modal state from the grid). Its dialog shell (PosModal, ModalHeroImage) is a ready-made frame a weight-entry dialog could reuse.

The product/variant admin form (CatalogAdminPage.jsx) already has a Sales UoM dropdown on create — but it's read-only after creation, and there is no "sold by weight" toggle or price-per-unit field anywhere in that form; a weighed variant is only implied by choosing KG/G as its unit.

F. Manual weight-entry proposal

Proposed — not built
  1. Trigger: a variant counts as weighed when salesUnitOfMeasure.allowsFractionalQuantity === true (and, once Phase B lands, an explicit sellingMode flag from the backend rather than inferring it from the unit).
  2. New dialog (e.g. WeightEntryDialog.jsx) built from the existing PosModal + NumericKeypadCore, with allowDecimal: true, maxDecimalPlaces: 3 (2 is not enough for 1.350 kg). Shows price/unit and an indicative price × weight preview, clearly labelled as an estimate — the authoritative number always comes back from the server. Or, as a smaller first step, reuse NumericKeypadModal as-is with maxDecimalPlaces=3 — no new component, just no subtotal preview and some hardcoded Arabic strings to fix along the way.
  3. Backend call: extend addSellableVariant to accept an explicit quantity instead of the hardcoded 1/+1; each weighing most likely becomes its own cart line (skip the "existing line, +1" merge for weighed variants, since two separately-weighed pieces of the same fish are not interchangeable).
  4. Card UI: for a weighed variant, replace the ±1 stepper/row with a single "Weigh" action that opens the dialog, and display quantity with its unit symbol and fixed decimals instead of a raw float.
  5. Cart editing: the existing quantity-edit dialog (POSPage.jsx, modal === "editQuantity") is hardcoded to allowDecimal={false} — this needs to read the line's unit. Because it's currently delta-based, editing a weight (e.g. 1.35 → 1.20) risks floating-point drift; adding a true setQuantity(lineId, absoluteValue) to useDraftLineEditor is the cleaner fix.
  6. No new API contract is needed on the frontend side if the backend already accepts a decimal quantity (it does) — this is a UI-and-wiring change, not a contract change.

Open risk The inventory stock indicator on the product card currently floors to whole units (Math.floor) — not meaningful for weighed stock and needs its own display logic.

G. Electronic scale / Edge Agent integration

Verified

In one line: the Edge Agent can already find a scale's port or USB descriptor, but it cannot read a byte of data from any device, and there is no channel at all — today — for a reading to travel from the agent to the POS. Every style below except keyboard-wedge needs new plumbing in both directions.

The agent is a pull-only Windows Service: it polls /heartbeat and /configuration every 30s, and /print-jobs/next every 5s. It hosts no local server of any kind — a browser on the same machine cannot talk to it directly. A code comment explicitly rules out SignalR: "reuse the existing mechanism, no aggressive polling, no SignalR."

The backend's device model is already generic enough. DeviceType.Scale = 8 already exists in src/Nobo.Domain/Devices/DeviceType.cs — a scale can be registered, bound to a serial/USB/network candidate, and delivered to the agent today with zero domain change. DeviceHardwareBinding already stores serial settings (BaudRate, DataBits, Parity, StopBits) via SetDeviceSerialSettings — but a code comment there admits "nothing in the Edge Agent reads these values yet," and EdgeRuntimeConfigurationQuery doesn't even forward them to the agent's runtime snapshot yet.

H. Inventory implications

Verified

ProductVariantInventoryComponent.QuantityPerSalesUnit (numeric(28,8), must be > 0) is the only link between a variant's selling unit and an inventory item's stock unit. SetProductVariantInventoryComponentHandler checks the inventory item's own fractional-quantity rule against this value — but never compares the variant's sales unit to the item's base unit, and never checks dimension. A KG sale against a stock item tracked in G works only if someone configures QuantityPerSalesUnit = 1000 correctly; nothing catches a wrong factor, and a KG sale against an EA-tracked item is accepted with no error at all.

Consumption, in ConfirmSalesOrderHandler.ApplyInventoryConsumptionAsync, computes requiredQuantity = requirement.Quantity * line.Quantity — already decimal-safe. 1.350 kg deducts correctly once the component factor is right. If the stock unit isn't fractional and the result isn't a whole number, confirmation fails cleanly with Inventory.QuantityPrecisionInvalid.

Insufficient stock is handled by a guarded single UPDATE (quantity_on_hand >= qty) — stock can never go negative, and a short debit fails the whole confirmation with Inventory.InsufficientStock, atomically.

F (wastage/trimming/cooking loss): not a current capability at all — today's model deducts exactly the measured sale weight, with no concept of a separate "raw weight bought vs. sellable weight after trimming." That's a legitimate future enhancement, clearly out of scope for this feature.

I. Kitchen / receipt / invoice / refund

Verified

The customer receipt renderer (CustomerReceiptEscPosRenderer.cs) prints "{qty} {symbol} x {name} ... {total}" — quantity formatted as "0.####", so 1.350 kg prints as "1.35 kg". It never prints the unit price, even though it's present in the payload — so "@ 250.00 EGP/kg" is simply not shown today. The kitchen ticket behaves the same way for quantity/symbol and should already work correctly for a weighed item.

Invoice lines use higher precision (numeric(28,8)) and format values with plain ToString(InvariantCulture) — no fixed decimal count — so a weighed invoice line could print something like "1.35000000 kg" or "250.00000000 EGP/kg" unless this is fixed.

Credit notes / refunds (CreditNotePlanner) already take a decimal partial quantity (> 0, ≤ remaining), prorate amounts, and round to currency digits — partial-weight refunds already work as-is.

What would need to change Only the receipt renderer (to print the unit price) and the invoice formatter (to fix the decimal places) — the data itself is already complete and correctly snapshotted everywhere; nothing is silently lost, just under-displayed.

Plain manual-entry weighed selling needs zero migration — every precision above already comfortably fits a 3-decimal-place kilogram weight.

A migration becomes necessary only for new, explicit semantics, and only this minimal version:

  1. ProductVariant: add SellingMode (int, not null, default 1 = PerUnit; 2 = ByWeight) — or derive it from the unit's dimension being Mass, which needs no column but stays implicit.
  2. SalesOrderLine: snapshot the selling mode (or unit dimension) at sale time — int, not null, default 1. Optionally add a nullable weight-source column (Manual/Scale) for audit.
  3. Optionally mirror the same snapshot onto CustomerReceiptLine and KitchenTicketItem.
  4. Only if real cross-dimension unit conversion is wanted: a ToBaseFactor numeric(28,8) on UnitOfMeasure plus seed updates — the alternative is to keep relying on the existing QuantityPerSalesUnit and add validation only, no schema change.

Every existing record stays fully compatible: a default of PerUnit on every column leaves every historical row's meaning unchanged, and the existing price × quantity formula already produces the correct weighed result with no formula change.

Selling a product never touches product/price configuration — those boundaries are already clean and would stay that way. The client cannot dictate its own unit price or line total today — the add-line command carries only variant id, quantity, and modifier option ids; every price comes from the database inside the handler, and the payable amount is always server-computed. The client does control quantity — i.e., the weight — today bounded only by "> 0, ≤ 4 decimals, whole-number-if-the-unit-says-so." There's no upper bound and no record of where that number came from (typed by the cashier vs. reported by a scale) — worth deciding deliberately once a scale exists, so a disconnected or stale scale can't silently let an old/garbage reading through unflagged.

Default behavior for every existing unit-based product, exactly as it is today: an EA variant has AllowsFractionalQuantity = false, so only whole quantities are ever accepted; subtotal = (price + modifiers) × quantity; consumption = QuantityPerSalesUnit × quantity. None of this changes under the proposed design — new behavior only activates behind a new, defaulted-to-off flag.

N. Risks, blockers & open questions

  1. 1Modifier pricing policy for weighed items is undecided — a per-weight-unit adjustment multiplies oddly against a fractional quantity.
  2. 2No check today that a variant's sales unit and its linked inventory item's stock unit even measure the same thing — a wrong QuantityPerSalesUnit factor fails silently.
  3. 3No field anywhere records that a sale was weighed, or where the weight came from (manual vs. scale) — matters for audit once a scale exists.
  4. 4No upper bound on quantity/weight, and no tare-weight concept.
  5. 5Line subtotals aren't rounded to currency digits (only the order payable is) — receipt lines can fail to sum exactly to the printed total.
  6. 6The printed customer receipt omits the unit price entirely; invoice amounts may print with 8 raw decimal places.
  7. 7GetSellableVariantsAsync doesn't filter inactive units — an unrelated small bug found along the way.
  8. 8A variant's sales unit is fixed forever at creation — converting an existing piece-based product to weighed means creating a new variant, not editing the old one.
  9. 9PriceListItem.Amount never records which unit it's priced per — safe only because the unit can't change today.
  10. 10The existing quantity-edit keypad defaults to 2 decimal places and has several hardcoded Arabic strings outside the i18n system.
  11. 11Every quantity control in the POS today is delta-based (±1); there is no "set to this exact value" call, risking float drift when editing a weight.
  12. 12A keyboard-wedge scale's output, ending in Enter, could be misread by the existing barcode-wedge detector if no input is focused when it fires.
  13. 13The product card's stock indicator floors to whole units — not meaningful once stock itself is weighed.
  14. 14Every Edge Agent↔cloud channel is slow-polling (30s heartbeat) or purpose-built for print jobs only — nothing can carry a live measurement without new plumbing, and no reading reaches the POS by any existing path.
  15. 15A stored serial binding is keyed only by COM port number, which Windows can reassign on a USB replug — the binding would silently point at the wrong port.
  16. 16No scale vendor or protocol is implemented or known; Phase G cannot start until a specific manufacturer's documentation is in hand.
  17. 17Whether "sold by weight" should be an explicit column or inferred from the unit's dimension is a real design choice with different blast radii — Phase A should settle it before any code is written.
