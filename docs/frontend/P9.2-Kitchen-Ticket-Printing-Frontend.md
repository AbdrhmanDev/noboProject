## 2. UI changed

- **`src/features/kitchen/hooks/useKitchen.ts`**: two additions.
  - `useKitchenTicketPrintJobs(companyId, branchId, enabled)` — read-only wrapper around the EXISTING
    `getPrintJobs` API call, filtered to `documentType: "KitchenTicket"`, polling every 15s (the same
    cadence the kitchen board's own ticket queries already use) and stopping when `enabled` is false.
    It never calls anything that creates a print job.
  - `usePrintJobsByDocumentId(printJobs)` — a small memoized `Map<documentId, PrintJob>` so each
    ticket can look up its own job by `kitchenTicketId` in O(1).
- **`src/Pages/KitchenPage/KitchenPage.jsx`**: checks `Devices.View` (`useHasPermission(companyId,
  "Devices.View")`), calls the new hook only when both `Kitchen.View` (already required to load the
  board at all) and `Devices.View` are held, builds the ticket→job map, and passes `printJob` +
  `showPrintStatus` into each `KitchenTicketCard`.
- **`src/features/kitchen/components/KitchenTicketCard.jsx`**: a new, optional status row (only
  rendered when `showPrintStatus` is true) showing:
  - the real `PrintJobStatusBadge` (reused component) when a matching `PrintJob` was found, and
  - `PrintJobErrorMessage` (reused component) additionally when that job's status is `Failed`, or
  - a distinct "no print job found" line when none matched at all (§4's "unavailable").
- **`src/features/sales-orders/hooks/useDraftSalesOrder.ts`** (`useConfirmSalesOrder`): after a
  successful confirm, in addition to the existing draft-details invalidation, now also invalidates
  every cached print-jobs query for that company+branch (`[...printJobQueryKeys.all, companyId,
  branchId]`) so the Kitchen board's print-status read (and the Devices admin print-jobs list, if
  open) reflect the job(s) the backend just created, without waiting for the next poll tick.
- **`src/features/devices/types/devices.types.ts`**: added `take?: number` to `PrintJobsListFilters`
  — the real `GetPrintJobsQuery.Take` parameter was already accepted by the backend but not
  previously exposed in this type; used to cap the kitchen board's own list request.
- **`src/i18n/translations.js`**: 2 new keys, `printing.kitchenTicket.label` /
  `printing.kitchenTicket.unavailable`, ar/en/es/de (every other status/error string reused is
  already translated via the existing `printing.*` namespace).

## 3. Print status behavior

- **No new print request is ever created by the frontend.** Every call added is a `GET`; the backend
  already creates the `KitchenTicket` `PrintJob`(s) on order confirmation (P9.2, verified server-side,
  unchanged).
- Status is read from the **exact** backend value (`Queued | Claimed | Printing | Succeeded |
  Failed`) via the already-existing `PrintJobStatusBadge`/`getPrintJobStatusLabelKey` mapping — no
  new status vocabulary was introduced.
- **"Unavailable"** (from the task's suggested state list) is represented honestly as a **UI-only**
  condition — "no `PrintJob` row was found for this ticket's `documentId`" — never as if it were a
  5th backend enum member. It can legitimately happen for a ticket created before this read was wired
  up, or in the brief window between order confirmation and the list actually being (re)fetched.
- Gated on **`Devices.View`** (the endpoint's real requirement, distinct from `Kitchen.View`): a
  kitchen-only user without `Devices.View` sees the kitchen board exactly as before, with no print
  status section and no failed request — never a 403 surfaced as an error.
- Polls every 15s (matching the board's own existing cadence) and is explicitly invalidated right
  after POS confirmation for a fast first update.

## 4. Retry / reprint availability

**Not implemented — no such endpoint exists.** `PrintJobEndpoints.cs` exposes only the two `GET`
routes; there is no `POST .../retry`, `.../reprint`, `.../requeue` or equivalent anywhere in
`Nobo.Api.Devices` or the print-job Application handlers. Per the task's explicit instruction
("Otherwise do not fake one"), no retry/reprint button, action, or client-side re-request was added.
A `Failed` kitchen ticket print job is shown with its real status and error message (via the reused
`PrintJobErrorMessage`) so staff can see and act on it manually (e.g. via the existing Devices
print-job admin view, or a physical reprint procedure) — but the frontend never re-triggers printing
itself.

## 5. Kitchen vs. receipt printing — kept independent

- The new read (`useKitchenTicketPrintJobs`) filters `documentType: "KitchenTicket"` explicitly and
  is only wired into the Kitchen board; `CustomerReceipt` print jobs are never touched, queried, or
  displayed by this change.
- The `useConfirmSalesOrder` invalidation added is scoped to print-jobs broadly (company+branch), but
  since it invalidates by cache key prefix rather than fetching anything itself, it does not create,
  read, or display any receipt-specific data — it just marks that cache stale so whichever screen is
  open (Kitchen board, Devices print-jobs list) refetches its own, already-filtered query.
- No change was made anywhere in the settlement/payment flow. Kitchen ticket printing is already
  triggered by confirmation (backend, unchanged); this task adds no payment-time behavior, and no
  receipt-print UI was touched.
