# P9.1 — POS Invoice Printing and Printer Routing — Frontend

Frontend-only. **No backend, EdgeAgent, or API contract was modified.** Every endpoint used already existed and was verified against the real backend source before use.

## 1. Backend endpoints inspected (all pre-existing, none invented)

| Endpoint | Purpose | Used for |
| --- | --- | --- |
| `GET /api/companies/{companyId}/branches/{branchId}/devices?deviceType=&status=` | List devices, server-filterable | Branch printer-routing status; resolving the manual-print device |
| `PUT /api/.../devices/{deviceId}/status` | Activate/deactivate a device | Already existed; reused as-is (the *only* way to change routing outcome — see §3) |
| `GET /api/.../print-jobs?documentType=` | List print jobs, filterable by document type | Finding the PrintJob(s) already created for a receipt |
| `GET /api/.../print-jobs/{printJobId}` | Print job detail | Not newly used (list already carries everything the UI needs) |
| `GET /api/.../sales-orders/{salesOrderId}/receipt` | The receipt already issued on full settlement | Resolving `customerReceiptId` from the POS payment screen |
| `POST /api/.../sales-orders/receipts/{customerReceiptId}/print` | Manual print/reprint (`Nobo.Api.Sales.SalesOrders.PrintCustomerReceiptAsync`) | The explicit Print/Reprint action |
| `POST /api/.../sales-orders/{salesOrderId}/payments` | Receive payment (unchanged) | Confirmed it does **not** need to change — the backend's own auto-print already fires server-side |

Confirmed by reading `DeviceEndpoints.cs`, `PrintJobEndpoints.cs`, `SalesOrderEndpoints.cs`/`SalesOrderEndpointContracts.cs` directly. **No branch-level "set printer routing" endpoint exists**, and none was invented — see §3.

## 2. Printer management — reused, not duplicated

`features/devices` (an already-mature feature: `DevicesListPage`, `useDevices`, `DeviceStatusBadge`, `usePrintJobs`, `PrintJobStatusBadge`, `PrintJobErrorMessage`) already fully manages printer-capable devices: name, code, `deviceType` (including `ReceiptPrinter`), branch (implicit via `BranchContext`), `status` (Active/Inactive), `healthStatus`, `certificationStatus`. **Nothing new was built here** — no parallel Printer entity, no new list, no new detail page. The only addition is the routing-status widget in §3.

One real type gap was found and fixed: `PrintJobResponse` (frontend) was missing `documentId`, even though the real backend contract (`PrintJobResponse.DocumentId` / `PrintJobListItemResponse.DocumentId`) always returns it. Added the field to the existing type — a contract-accuracy fix, not new behavior.

## 3. Branch printer routing UI

Backend routing is **derived, not configured**: `PrintTargetResolver` resolves the branch's receipt printer as "the branch's one active `ReceiptPrinter` device, or fail closed if none/several" — there is no persisted "branch routing" setting and no endpoint to write one. Accordingly, the frontend adds a **read-only status widget**, `ReceiptPrinterRoutingStatus` (`features/devices/components/`), embedded at the top of `DevicesListPage`, computed with the **exact same query** the resolver itself uses server-side (`GET /devices?deviceType=ReceiptPrinter&status=Active`):

- **Zero** active receipt printers → "no active receipt printer; no auto-print job will be created until one is activated."
- **Exactly one** → "Ready — will print on `{name}`."
- **Several** → "ambiguous; keep only one active" (styled distinctly, amber) — the exact same ambiguity the backend refuses to guess at.

Clicking it jumps to the existing device list filtered to `ReceiptPrinter`. **Fixing** an unconfigured/ambiguous state means activating/deactivating a device with the page's existing actions — no new write path was added, because none exists on the backend. No Terminal-level selection, no `DefaultPrinterDeviceId`, no client-only precedence rule was added, per the explicit instruction.

## 4. Manual print / reprint

New component `ReceiptPrintPanel` (`features/payments/components/`), using the real `POST .../receipts/{customerReceiptId}/print` endpoint via a new `usePrintCustomerReceipt` mutation:

- **Print** shown when no `PrintJob` exists yet for the receipt; **Reprint** shown once one does (any status) — never presented as "a new invoice": the button always targets the same, already-issued, immutable `CustomerReceiptId`.
- The device passed is the branch's resolved single active `ReceiptPrinter` (same resolution as §3); the button is disabled (no device to send) when routing is unconfigured or ambiguous — never guesses.
- A **fresh** `Idempotency-Key` header is generated on every click (`createPaymentIdempotencyKey`, the same helper already used for `receiveSalesOrderPayment`/`refundSalesOrderPayment`), so every explicit click is a genuinely new print request — reprinting never mutates the receipt, invoice, or payment; it only ever creates another `PrintJob` row.
- Status is shown via the **existing** `PrintJobStatusBadge`/`PrintJobErrorMessage` components (`features/devices`), reused unchanged — no new status vocabulary was invented; only backend-exposed statuses (`Queued`/`Claimed`/`Printing`/`Succeeded`/`Failed`) are ever displayed.

## 5. Auto-print — frontend does nothing extra

Per the explicit instruction, **the frontend never calls the print endpoint after a successful payment.** `ReceiveSalesOrderPaymentHandler`'s own `onSuccess` (in `usePayments.ts`) was extended by exactly one line: invalidate the new `customerReceipt` query key, so the receipt (and, once claimed, its `PrintJob`) becomes visible once React Query refetches. Nothing constructs or sends a print request from the payment success path.

## 6. Print failure semantics

`ReceiptPrintPanel` renders independently of payment status — it only appears once `useCustomerReceiptForSalesOrder` resolves a receipt (i.e., payment already succeeded), and a `Failed` `PrintJob` only ever renders the existing `PrintJobErrorMessage`, never any payment-related text. The panel cannot appear as, or be confused with, a payment failure — it has no visual or logical connection to the payment success card other than sitting inside it. States shown, all backend-exposed: **Print queued** / **Print claimed** / **Printing** / **Print failed** (with the real error) / **Reprint available** (any terminal state) / **no printer configured** / **ambiguous printer**. No invented status was added.

## 7. Template integration

Untouched. Neither `ReceiptPrintPanel` nor anything else in this change renders receipt content — no line items, totals, or layout are drawn client-side. The backend pipeline (`Invoice → Effective Template → RenderedDocument → PrintJob → Printer`, or for POS receipts specifically, `CustomerReceipt → read model → PrintJob payload → EscPosPrinterAdapter → CustomerReceiptEscPosRenderer`) remains exactly as it was; the frontend only displays the `PrintJob`'s **status**, never its content.

## 8. Permissions

- **Manual print**: gated on `Pos.PrintReceipt` (the real, existing backend permission — verified in `ApplicationPermissions.PosPrintReceipt`/`PrintCustomerReceiptHandler`), checked via the existing `useHasPermission` hook. `ReceiptPrintPanel` renders nothing at all for a user without it.
- **Device/printer management**: unchanged — `DevicesListPage` already separately gates create/edit on `Devices.Manage` and viewing on `Devices.View`; the new routing-status widget only reads (`Devices.View` scope, same as the rest of the page).
- **Branch configuration**: N/A — there is no branch-level printer configuration endpoint to gate (see §3).

No permission name was invented; no parallel authorization system was added.

## 9. Routes / navigation

No new route or page. `ReceiptPrinterRoutingStatus` was added to the existing `DevicesListPage` (reached via the existing Devices nav item); `ReceiptPrintPanel` was added to the existing POS payment-complete screen (`CompleteStep`, inside the existing POS page/route). Per the explicit instruction to prefer `Devices → Printers`-style integration over a new page, no `Branches → Printer Routing` page was created — the routing status lives where the printers themselves are already managed.

## 10. Backend gaps found (documented, not faked)

1. **No endpoint to fetch the `PrintJob`(s) for a specific document directly.** `GET /print-jobs` supports `documentType` but not `documentId`. Worked around by fetching the branch's `CustomerReceipt` jobs and filtering by `documentId` client-side (a small, bounded list — POS branches don't have unbounded receipt-print volume) rather than inventing a new query parameter. If this becomes a real limitation (e.g. once a branch accumulates many receipts), a `documentId` filter on the existing endpoint would be the natural, minimal backend addition — not proposed here since it wasn't required to ship this feature correctly.
2. **`ReceiveSalesOrderPaymentResult` does not return the issued `CustomerReceiptId`/`InvoiceId`.** The frontend instead calls the separate `GET .../sales-orders/{salesOrderId}/receipt` endpoint after payment succeeds. This works correctly and needed no workaround, but is worth noting: a future payment-result enhancement could return the receipt id directly and save one round trip.

Neither gap blocked this phase; both are documented rather than papered over with an invented endpoint.

## 11. Error handling

Uses the app's existing `normalizeApiError`/`ApiError` shape throughout (`error.message` shown as-is on a failed print/reprint call) — no invented error text, no fabricated compliance/business rule. The receipt query itself uses `retry: false` and is simply not rendered when the query hasn't resolved (an order not yet fully paid is an expected state, not an error to display).

## 12. i18n / RTL

All new user-facing strings go through `useI18n()`/`t()`. New keys added to **all four** existing languages (`ar`, `en`, `es`, `de`), matching this repo's established convention (verified against several existing keys already present in all four sections):

No user-facing string is hardcoded. RTL is inherited automatically (the app already sets `dir`/`lang` globally via `I18nProvider`; no new layout assumes LTR).
